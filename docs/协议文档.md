# 广理职小鱼 · 通信协议文档

> 这是客户端（C#）和服务器（C）之间的"合同"。两边都按这份文档写，就能对上。
> **任何人都不要私自改协议**。觉得哪里不合理，先在群里提出来。

---

## 1. 连接方式

- 协议：TCP **长连接**。客户端启动时连上服务器，一直保持，退出程序才断开。
- 默认端口：`9527`
- 线上服务器 `server.aaalez.com:443` 外面多一层 **TLS 加密**：客户端先做 TLS 握手（校验证书是不是这个域名的），之后在加密通道里收发的内容和下面写的完全一样。服务器程序本身不变，加密由前面的 nginx 负责（见《部署说明》）
- 心跳：客户端每 **30 秒**发一次 `sys.ping`。服务器 **120 秒**没收到任何消息，就认为客户端掉线，主动断开。

## 2. 消息格式（帧）

TCP 是"字节流"，不知道一条消息在哪结束（这叫**粘包/半包问题**）。所以每条消息前面加 4 个字节，写明后面 JSON 有多长：

```
+--------------------+-----------------------------+
| 长度 L（4 字节）    | JSON 正文（L 字节，UTF-8）   |
+--------------------+-----------------------------+
```

- 长度用**大端序**（网络字节序）：比如长度 300 = `00 00 01 2C`。
- 正文是 UTF-8 编码的 JSON。
- 单条消息最大 **8 MB**。超过的话服务器直接断开连接。

## 3. 三种消息

### 3.1 请求（客户端 → 服务器）

```json
{
  "id": 12,
  "cmd": "user.login",
  "token": "登录后拿到的 token，没登录可以不写",
  "data": { "username": "alice", "password": "Ab123456" }
}
```

| 字段 | 说明 |
|---|---|
| `id` | 请求编号，客户端自己从 1 开始递增。服务器回复时原样带回，客户端靠它把回复和请求对上 |
| `cmd` | 命令名，格式是 `模块.动作` |
| `token` | 登录后服务器给的令牌。需要登录的命令必须带 |
| `data` | 参数，每个命令不一样，见第 6 节 |

### 3.2 回复（服务器 → 客户端）

```json
{ "id": 12, "code": 0, "msg": "ok", "data": { ... } }
```

| 字段 | 说明 |
|---|---|
| `id` | 对应请求的编号 |
| `code` | 错误码，`0` 表示成功，见第 4 节 |
| `msg` | 成功时是 `"ok"`；失败时是给用户看的中文提示，比如 `"密码错误"` |
| `data` | 成功时是结果；失败时是空对象 `{}` |

### 3.3 推送（服务器主动发给客户端）

```json
{ "push": "chat.new_message", "data": { ... } }
```

推送**没有** `id`，客户端看到有 `push` 字段就知道这是推送。事件列表见第 7 节。

## 4. 错误码

| code | 含义 | 例子 |
|---|---|---|
| 0 | 成功 | |
| 400 | 参数错误 | 缺字段、格式不对、太长太短 |
| 401 | 未登录或登录已过期 | 没带 token，或者 token 过期 |
| 402 | 余额不足 | 买东西钱不够 |
| 403 | 没有权限 | 改别人的商品、买自己的商品、被禁言时发私信、不是管理员却用 `admin.*` 命令 |
| 404 | 不存在 | 用户、商品、订单找不到 |
| 409 | 状态冲突 | 用户名已被注册、商品已卖出、订单状态不允许这个操作 |
| 413 | 数据太大 | 图片超过 5 MB |
| 500 | 服务器内部错误 | 数据库出错 |
| 501 | 还没实现 | 开发阶段，功能还没写完 |

## 5. 数据约定

- **金额一律用"分"，整数**。`1500` 表示 15.00 元。不用小数是为了避免 `0.1 + 0.2 ≠ 0.3` 这种误差。客户端显示时除以 100。
- **时间一律用 Unix 时间戳（秒）**，整数。客户端自己转成"3 分钟前"这类文字。
- **id 都是正整数**。
- **图片**：先用 `file.upload` 上传，拿到一个图片名（如 `3f9a…e1.jpg`），再把图片名填到其他命令里。显示图片时用 `file.get` 按图片名取。
- **字数**按"字符"算，一个汉字算 1 个字。
- 可选字段不传，就当没有。

### 5.1 公共对象

下面这些对象在很多命令里都会用到。

**UserBrief（用户简要信息）**
```json
{ "user_id": 1001, "nickname": "阿狸", "avatar": "图片名或空字符串" }
```

**UserInfo（自己的完整信息）**
```json
{
  "user_id": 1001, "username": "alice", "nickname": "阿狸",
  "avatar": "", "bio": "个人简介", "balance": 50000, "created_at": 1762500000,
  "email": "alice@example.com", "is_admin": false,
  "muted_until": 0, "nickname_locked_until": 0
}
```
- `email`：注册时验证过的邮箱（小写）；没绑邮箱的老账号是空字符串
- `is_admin`：是不是管理员（能登录审核后台）
- `muted_until`：禁言到什么时候，`0` 或早于现在 = 没被禁言
- `nickname_locked_until`：昵称因违规被重置后，到这个时间之前不能改昵称

**GoodsBrief（商品卡片，用在列表里）**
```json
{
  "goods_id": 2001, "title": "九成新山地自行车", "price": 32000,
  "cover": "第一张图片名，没图是空字符串", "status": "on_sale",
  "view_count": 15, "created_at": 1762500000, "reject_reason": "",
  "seller": { UserBrief }
}
```

**GoodsDetail（商品详情）** = GoodsBrief 的全部字段，再加上：
```json
{
  "description": "描述", "original_price": 80000,
  "category_id": 5, "category_name": "运动户外",
  "condition": 1, "images": ["a.jpg", "b.jpg"], "updated_at": 1762500000
}
```

- `status`：`on_sale` 在售 / `sold` 已卖出 / `off_shelf` 已下架 / `reviewing` 审核中（刚发布或刚修改，等 AI 审核）/ `rejected` 被驳回（违规下架）
- `reject_reason`：被驳回的原因，只有 `rejected` 时有内容
- `condition` 成色：`0` 全新 / `1` 几乎全新 / `2` 轻微使用痕迹 / `3` 明显使用痕迹
- `original_price` 原价：没填是 `0`

**Order（订单）**
```json
{
  "order_id": 3001, "order_no": "202611071530121234",
  "goods_id": 2001, "goods_title": "九成新山地自行车", "goods_cover": "a.jpg",
  "price": 32000, "status": "paid", "ship_note": "",
  "buyer": { UserBrief }, "seller": { UserBrief },
  "created_at": 1762500000, "shipped_at": 0, "completed_at": 0, "cancelled_at": 0
}
```

- `status`：`paid` 已付款待发货 / `shipped` 已发货 / `completed` 已完成 / `cancelled` 已取消
- 还没发生的时间是 `0`
- `goods_title` 和 `price` 是下单那一刻的**快照**：卖家之后改了商品，订单里的不会跟着变

**Message（聊天消息）**
```json
{
  "message_id": 5001, "from_id": 1001, "to_id": 1002,
  "goods_id": 2001, "content": "还在吗？", "is_read": false, "created_at": 1762500000,
  "flag": "none", "flag_kind": ""
}
```
- `goods_id`：这条消息关于哪件商品，没有就是 `0`。
- `flag`：`none` 正常 / `warn` 命中二级敏感词（接收方显示黄色提醒条和"举报"按钮）/ `masked` 已因违规屏蔽（这时 `content` 固定是"该消息因违规已被屏蔽"，原文只有审核后台能看到）
- `flag_kind`：命中的类别，见 6.7 节的类别表；`none` 时是空字符串

**Conversation（会话，聊天列表的一行）**
```json
{ "peer": { UserBrief }, "last_message": { Message }, "unread": 2 }
```

**分页列表** —— 所有带分页的命令都返回这个形状：
```json
{ "total": 57, "page": 1, "page_size": 20, "items": [ ... ] }
```
分页参数：`page` 从 1 开始，默认 1；`page_size` 范围 1–50，默认 20。超出范围按 400 处理。

## 6. 命令列表

标记说明：🔒 需要登录（请求要带 token，否则返回 401）；🛡 只有管理员能用（不是管理员返回 403）。

### 6.1 系统和文件（公共部分，已经写好）

#### `sys.ping` —— 心跳
- 请求：`{}`
- 返回：`{ "server_time": 1762500000 }`

#### `file.upload` 🔒 —— 上传图片
- 请求：`{ "ext": "jpg", "data": "图片的 Base64" }`
  - `ext` 只能是 `jpg` / `png` / `gif` / `webp`
  - 图片解码后最大 5 MB，超过返回 413
- 返回：`{ "image": "3f9a0c…e1.jpg" }`（32 位随机十六进制 + 扩展名）

#### `file.get` —— 下载图片
- 请求：`{ "image": "3f9a0c…e1.jpg" }`
- 返回：`{ "data": "图片的 Base64" }`
- 图片名格式不对返回 400，图片不存在返回 404

### 6.2 用户（负责：组员C）

#### `user.send_code` —— 发邮箱验证码
- 请求：`{ "email": "alice@example.com", "purpose": "register" }`
  - `purpose`：`register` 注册（默认，邮箱必须**没**注册过，否则 409）/ `reset` 找回密码（邮箱必须**已**注册，否则 404）
- 规则：
  - 验证码 6 位数字，**10 分钟**内有效，输错 5 次作废
  - 同一个邮箱 **60 秒**内只能发一次，太频繁 → 409 "发送太频繁，请 N 秒后再试"
  - 邮件发送失败 → 500
- 返回：`{ "expires_in": 600 }`
- 开发模式（服务器没配邮箱）：不真的发邮件，验证码写进服务器日志，并在返回里多一个 `"dev_code": "123456"`，方便测试

#### `user.register` —— 注册
- 请求：`{ "username": "alice", "password": "Ab123456", "nickname": "阿狸", "email": "alice@example.com", "code": "123456" }`
- 规则：
  - `username`：3–20 个字符，只能是英文字母、数字、下划线
  - `password`：8–32 个字符，且同时包含数字、大写字母和小写字母
  - `nickname`：1–20 个字；含一级敏感词 → 400；可以和别人重名
  - `email` + `code`：服务器配置 `require_email = 1` 时必填（线上服务器就是）；验证码不对 → 400 "验证码不对"，过期或输错太多次 → 400 "验证码已失效，请重新获取"。一个邮箱只能注册一个账号
  - 用户名或邮箱已被注册 → 409
  - 新用户余额为 0；注册后昵称会交给 AI 再审一遍（见 6.7）
- 返回：`{ "user_id": 1001 }`

#### `user.login` —— 登录
- 请求：`{ "username": "alice", "password": "Ab123456" }`（`username` 里带 `@` 就当邮箱登录）
- 规则：登录只核对密码是否正确，不检查强度（兼容旧账户）；用户名不存在或密码错误，都返回 **401**，提示统一为"用户名或密码错误"（不告诉别人到底是哪个错了，防止有人试探哪些用户名存在）
- 返回：`{ "token": "64 位十六进制", "user": { UserInfo } }`
- token 有效期 7 天

#### `user.logout` 🔒 —— 退出登录
- 请求：`{}`
- 作用：让当前 token 失效
- 返回：`{}`

#### `user.me` 🔒 —— 查看自己的信息
- 请求：`{}`
- 返回：`{ UserInfo }`

#### `user.update_profile` 🔒 —— 修改个人资料
- 请求：`{ "nickname": "新昵称", "avatar": "图片名", "bio": "简介" }`，三个字段都可选，传了哪个就改哪个
- 规则：`nickname` 1–20 个字；`bio` 0–100 个字；`avatar` 必须是已上传的图片（否则 400），空字符串表示清除头像
- 先把所有字段都检查完再改，不要改了一半才发现后面的字段不对
- 内容安全：昵称、简介含一级敏感词 → 400；昵称被重置后的 24 小时内改昵称 → 403；改了昵称或简介会交给 AI 再审（见 6.7）
- 返回：修改后的 `{ UserInfo }`

#### `user.change_password` 🔒 —— 修改密码
- 请求：`{ "old_password": "Ab123456", "new_password": "Cd654321" }`
- 规则：原密码不对 → 400；新密码规则和注册一样；新旧密码相同 → 400。改完后**其他设备**的登录全部失效，当前这个保留
- 返回：`{}`

#### `user.reset_password` —— 忘记密码（用邮箱验证码重置）
- 请求：`{ "email": "alice@example.com", "code": "123456", "new_password": "Cd654321" }`
- 规则：先用 `user.send_code`（`purpose: "reset"`）拿验证码；验证码规则同注册；重置后**所有设备**都要重新登录
- 返回：`{}`

#### `user.get` —— 查看别人的主页
- 请求：`{ "user_id": 1002 }`
- 返回：
  ```json
  { "user_id": 1002, "nickname": "小鱼", "avatar": "", "bio": "",
    "created_at": 1762500000, "on_sale_count": 3, "sold_count": 5 }
  ```
  `on_sale_count` 在售商品数，`sold_count` 已卖出商品数。**不返回** `username` 和 `balance`

#### `user.recharge` 🔒 —— 充值（模拟）
- 请求：`{ "amount": 10000 }`
- 规则：`amount` 1–1000000（即 0.01–10000 元）
- 返回：`{ "balance": 60000 }`（充值后的余额）

### 6.3 商品（负责：组员C）

#### `goods.categories` —— 分类列表
- 请求：`{}`
- 返回：`{ "items": [ { "category_id": 1, "name": "数码电子" }, ... ] }`
- 分类固定为：1 数码电子、2 书籍教材、3 生活用品、4 服饰鞋包、5 运动户外、6 美妆个护、7 其他

#### `goods.publish` 🔒 —— 发布商品
- 请求：
  ```json
  { "title": "九成新山地自行车", "description": "骑了一学期……",
    "price": 32000, "original_price": 80000,
    "category_id": 5, "condition": 1, "images": ["a.jpg", "b.jpg"] }
  ```
- 规则：
  - `title`：1–30 个字
  - `description`：0–500 个字，可不传
  - `price`：1–99999900（0.01–999999 元）
  - `original_price`：可不传；传了必须是 0–99999900
  - `category_id`：必须是存在的分类
  - `condition`：0–3，可不传，默认 2
  - `images`：0–9 张，每张都必须是已上传的图片（否则 400）；第一张是封面
  - 标题或描述含禁售词（代课代写、违禁品等）→ 400，提示里写明命中的类别和词
- 开了 AI 审核时，新商品先是 `reviewing`（审核中，别人搜不到），审核完推送 `goods.reviewed`（见 6.7）；没开就直接 `on_sale`
- 返回：`{ "goods_id": 2001, "status": "reviewing" }`

#### `goods.update` 🔒 —— 修改商品
- 请求：`{ "goods_id": 2001, ...要改的字段 }`，字段和 `goods.publish` 一样，都可选，规则也一样
- 规则：
  - 只能改自己的商品，否则 403
  - 已卖出的商品不能改 → 409
  - 传了 `images` 就整体替换原来的图片
  - 改了标题、描述、图片或分类，就要重新审核：在售、审核中、被驳回的商品变回 `reviewing`（被驳回的商品就是这样改好后重新提交的）；已下架的保持下架，但也会审一遍
- 返回：`{ "status": "reviewing" }`（修改后的商品状态）

#### `goods.off_shelf` 🔒 —— 下架
- 请求：`{ "goods_id": 2001 }`
- 规则：只能下架自己的商品（403）；只有 `on_sale` 能下架（409）
- 返回：`{}`

#### `goods.on_shelf` 🔒 —— 重新上架
- 请求：`{ "goods_id": 2001 }`
- 规则：只能操作自己的商品（403）；只有 `off_shelf` 能上架（409），所以被驳回的商品不能自己上架，只能修改后重新审核，或者申诉
- 返回：`{}`

#### `goods.detail` —— 商品详情
- 请求：`{ "goods_id": 2001 }`
- 规则：任何状态的商品都能看（买家要能看到自己买过的商品）；每查看一次，浏览量**先 +1 再返回**（第一次查看返回的 `view_count` 是 1）
- 返回：`{ GoodsDetail }`

#### `goods.search` —— 搜索 / 商品列表（首页用的就是它）
- 请求：
  ```json
  { "keyword": "自行车", "category_id": 5, "seller_id": 1001,
    "min_price": 1000, "max_price": 50000,
    "sort": "newest", "page": 1, "page_size": 20 }
  ```
  所有字段都可选。
- 规则：
  - **只返回在售（`on_sale`）的商品**
  - `seller_id`：只看这个卖家的商品（用户主页用）
  - `keyword`：标题**或**描述里包含这个词就算匹配；0–30 个字；空字符串等于不传。`%`、`_` 都当普通字符
  - `sort`：`newest` 最新发布（默认）/ `price_asc` 价格从低到高 / `price_desc` 价格从高到低 / `hot` 浏览量从高到低。其他值 → 400
  - 价格相同或浏览量相同时，新发布的排在前面；发布时间也相同，`goods_id` 大的在前
- 返回：分页列表，`items` 里是 `GoodsBrief`

#### `goods.mine` 🔒 —— 我发布的
- 请求：`{ "status": "on_sale", "page": 1, "page_size": 20 }`
  - `status` 可选：`on_sale` / `sold` / `off_shelf` / `reviewing` / `rejected`，不传就是全部
- 返回：分页列表，`items` 里是 `GoodsBrief`，最新发布的在前（发布时间相同，`goods_id` 大的在前）

### 6.4 订单（负责：组员D）

我们模拟闲鱼的**担保交易**：

```
买家下单 ──► 已付款(paid) ──卖家发货──► 已发货(shipped) ──买家确认收货──► 已完成(completed)
  钱从买家余额扣掉，                                                        这时钱才打给卖家
  先由平台"冻结"
              │
              └──买家或卖家取消──► 已取消(cancelled)：钱退回给买家，商品重新上架
```

#### `order.create` 🔒 —— 下单（立即付款）
- 请求：`{ "goods_id": 2001 }`
- 规则（**全部在一个数据库事务里完成**）：
  1. 商品不存在 → 404
  2. 买自己的商品 → 403
  3. 商品不是在售状态 → 409 "商品已卖出或已下架"
  4. 余额不够 → 402
  5. 商品状态改成 `sold`，扣买家余额，创建订单（状态 `paid`）
  6. 两个人同时买同一件商品时，**只能有一个人成功**，另一个人得到 409
- 订单号 `order_no`：`年月日时分秒` + 4 位随机数字，共 18 位，比如 `202611071530121234`
- 成功后**推送** `order.updated` 给卖家
- 返回：`{ Order }`

#### `order.cancel` 🔒 —— 取消订单
- 请求：`{ "order_id": 3001 }`
- 规则：买家和卖家都能取消（别人 → 403）；只有 `paid` 状态能取消（409）。取消后钱退回买家，商品改回 `on_sale`
- 成功后推送 `order.updated` 给**另一方**
- 返回：`{ Order }`

#### `order.ship` 🔒 —— 发货
- 请求：`{ "order_id": 3001, "ship_note": "明天中午食堂门口当面交易" }`
- 规则：只有卖家能发货（403）；只有 `paid` 能发货（409）；`ship_note` 0–100 个字，可不传
- 成功后推送 `order.updated` 给买家
- 返回：`{ Order }`

#### `order.confirm` 🔒 —— 确认收货
- 请求：`{ "order_id": 3001 }`
- 规则：只有买家能确认（403）；只有 `shipped` 能确认（409）。确认后订单金额加到卖家余额
- 成功后推送 `order.updated` 给卖家
- 返回：`{ Order }`

#### `order.detail` 🔒 —— 订单详情
- 请求：`{ "order_id": 3001 }`
- 规则：只有买家和卖家能看（403）
- 返回：`{ Order }`

#### `order.list` 🔒 —— 我买到的 / 我卖出的
- 请求：`{ "role": "buyer", "status": "paid", "page": 1, "page_size": 20 }`
  - `role` 必填：`buyer` 我买到的 / `seller` 我卖出的
  - `status` 可选，不传就是全部
- 返回：分页列表，`items` 里是 `Order`，按 `order_id` 从大到小（最新的在前）

### 6.6 聊天（负责：组员D）

#### `chat.send` 🔒 —— 发私信
- 请求：`{ "to_user_id": 1002, "content": "还在吗？", "goods_id": 2001 }`
- 规则：`content` 1–500 个字；不能发给自己（400）；对方不存在（404）；`goods_id` 可选，传了必须存在（404），传 0 等于不传
- 内容安全：
  - 被禁言 → 403，提示里有剩余时间
  - 含一级敏感词（人身攻击、色情低俗、政治敏感违法）→ 400，发不出去，服务器留底
  - 含二级敏感词（骚扰威胁、诈骗引流，比如"加微信""转账"）→ 照常发出，`flag` 是 `warn`；同时交给 AI，AI 有把握判违规就屏蔽这条消息并禁言发送者 12 小时
- 成功后**推送** `chat.new_message` 给对方
- 返回：`{ Message }`

#### `chat.history` 🔒 —— 聊天记录
- 请求：`{ "peer_id": 1002, "before_id": 5100, "limit": 20 }`
  - `before_id` 可选：只要 id 比它小的消息（往上翻更早的记录时用）
  - `limit` 1–50，默认 20
- 返回：`{ "items": [ Message, ... ] }`，取最近的 `limit` 条，**按时间从早到晚排**（方便直接显示）

#### `chat.conversations` 🔒 —— 会话列表
- 请求：`{}`
- 返回：`{ "items": [ Conversation, ... ] }`，最近有消息的会话排在前面

#### `chat.mark_read` 🔒 —— 标记已读
- 请求：`{ "peer_id": 1002 }`
- 作用：把对方发给我的消息全部标成已读
- 返回：`{ "updated": 3 }`（这次标记了几条）

#### `chat.unread_count` 🔒 —— 未读总数
- 请求：`{}`
- 返回：`{ "count": 5 }`

### 6.7 内容安全（举报、申诉）

**审核规则一览**（服务器自动执行，AI = TypeSafe 的 Jev 决策模型，"有把握" = 概率 ≥ 0.9）：

| 内容 | 一级敏感词 | 之后 |
|---|---|---|
| 私信 | 拦下不发（400） | 二级词：照常发出 + 接收方提醒 + AI 审；AI 有把握违规 → 屏蔽 + 禁言 12 小时 |
| 商品 | 拦下不发（400） | 先"审核中"，AI 有把握合规 → 上架；有把握违规 → 驳回下架；没把握或 AI 出错 → 先上架，交人工 |
| 昵称、简介 | 拦下（400） | AI 有把握违规 → 昵称改成"小鱼用户{编号}"、清空简介、24 小时内不能改昵称；没把握 → 交人工 |

所有自动处理都记进审核后台的"已自动处理"，管理员可以确认或撤销；拿不准的进"人工待审"。

**类别**（`flag_kind`、举报的 `type`、AI 判断结果都用这些代号）：

| 代号 | 名称 | 用在 |
|---|---|---|
| `abuse` | 人身攻击 | 私信、昵称简介 |
| `porn` | 色情低俗 | 私信、商品 |
| `political` | 政治敏感 | 私信、商品 |
| `illegal` | 违法违禁 | 私信 |
| `threat` | 骚扰威胁 | 私信（二级词） |
| `scam` | 诈骗引流 | 私信（二级词）、商品（刷单兼职、校园贷等） |
| `cheating` | 代课代写 | 商品 |
| `contraband` | 违禁品 | 商品 |
| `identity` | 证件账号 | 商品 |
| `other` | 其他 | 只用在举报类型 |

#### `report.create` 🔒 —— 举报一条私信
- 请求：`{ "message_id": 5001, "type": "abuse", "reason": "骂人" }`
- 规则：
  - `type`：`abuse` / `porn` / `political` / `threat` / `scam` / `other`
  - `reason`：1–200 个字
  - 只能举报别人发给你的消息（403）；消息已经被屏蔽 → 409；同一条消息只能举报一次 → 409
- 处理：AI 分两次**独立**判断——① 这条消息本身是否明确违规（严格，看不到举报理由）② 举报理由是否成立（宽松，不友善也算）。
  ① ≥ 0.9 → 屏蔽消息 + 禁言 12 小时；① 和 ② 都 ≤ 0.1 → 自动驳回举报；其余 → 人工判断。处理完推送 `report.result` 给举报人
- 返回：`{ "report_id": 1, "status": "pending" }`（`pending` 等 AI；没开 AI 时是 `manual` 等人工）

#### `appeal.create` 🔒 —— 申诉
- 请求：`{ "kind": "mute", "content": "我只是发了联系方式" }` 或 `{ "kind": "goods", "goods_id": 2001, "content": "这是正规家教" }`
- 规则：
  - `kind`：`mute` 申诉禁言（现在没被禁言 → 409）/ `goods` 申诉商品被驳回（只能申诉自己的、状态是 `rejected` 的商品）
  - `content`：1–200 个字
  - 同一件事已经有待处理的申诉 → 409
- 申诉直接进"人工待审"，管理员同意后自动解除禁言 / 恢复上架
- 返回：`{ "appeal_id": 1 }`

### 6.8 审核后台（管理员）

审核后台网页（`client/XiaoYu.Admin`）通过下面这些命令工作，客户端用不到。管理员用服务器命令设置：`xiaoyu_server 配置文件 --set-admin 用户名`。

**Case（审核案件）**
```json
{
  "case_id": 12, "area": "manual", "kind": "report", "ref_id": 3,
  "user": { UserBrief }, "summary": "一句话说明", "ai_label": "abuse", "ai_score": 0.75,
  "status": "open", "result": "", "created_at": 1762500000, "handled_at": 0
}
```
- `area`：`auto` 已自动处理（等人工复核）/ `manual` 人工待审
- `kind` 和 `ref_id`：`goods` 商品编号 / `chat` 消息编号（二级词私信被 AI 处理）/ `report` 举报编号 / `appeal` 申诉编号 / `profile` 用户编号
- `user`：当事人（被审核或被处理的人）
- `ai_score`：AI 判断"违规"的概率，`-1` 表示 AI 没判（比如 AI 调用失败、申诉）
- `status`：`open` 待处理 / `closed` 已结案（`result` 是处理结果）

| 命令 | 请求 | 返回 |
|---|---|---|
| `admin.stats` 🛡 | `{}` | `{ manual_open, auto_open, reviewing_goods, rejected_goods, muted_users, blocked_total, reports_total, pending_jobs, ai_enabled }` |
| `admin.cases` 🛡 | `{ "area": "manual", "status": "open", "page": 1, "page_size": 20 }`（`area`、`status` 可选） | 分页列表，`items` 是 Case，新的在前 |
| `admin.case_detail` 🛡 | `{ "case_id": 12 }` | `{ "case": Case, ... }`，再按 `kind` 附上详情，见下 |
| `admin.resolve` 🛡 | `{ "case_id": 12, "action": "punish", "note": "备注", "hours": 24 }` | `{ "result": "人工处理：……" }` |
| `admin.mute` 🛡 | `{ "user_id": 1001, "hours": 24 }`（1–720） | `{ "muted_until": 1762586400 }`，在原禁言结束时间上往后加 |
| `admin.unmute` 🛡 | `{ "user_id": 1001 }` | `{}` |
| `admin.users` 🛡 | `{ "keyword": "ali", "muted_only": true, "page": 1 }`（都可选） | 分页列表：`{ user_id, username, nickname, email, is_admin, muted_until, created_at, violations }`，`violations` = 他作为当事人的私信和举报案件数 |
| `admin.goods` 🛡 | `{ "status": "rejected", "page": 1 }` | 分页列表：`{ goods_id, title, price, status, reject_reason, created_at, seller }`，包括审核中和被驳回的 |
| `admin.blocked` 🛡 | `{ "kind": "chat", "page": 1 }`（`kind`：`chat` / `goods` / `profile`，可选） | 分页列表：`{ id, kind, user, category, category_label, word, content, created_at }` = 被一级词拦下的内容 |

`admin.case_detail` 按 `kind` 附带的内容：
- `goods`：`goods`（标题、描述、价格、状态、驳回原因、分类名、卖家、图片）
- `chat`：`message`（**原文**，即使已屏蔽）、`sender`、`receiver`、`sender_muted_until`、`context`（前后最多 11 条对话，`is_target` 标出是哪一条）
- `report`：`report`（举报人、类型、理由、状态、`ai_violation` / `ai_category` / `ai_reason` 两次 AI 判断）+ 和 `chat` 一样的消息和对话
- `profile`：`profile`（用户名、昵称、简介、邮箱、禁言、昵称锁定）
- `appeal`：`appeal`（类型、内容、状态）、`user_muted_until`，商品申诉再附 `goods`

`admin.resolve` 的 `action`（`note` 可选，最多 200 字）：

| 案件 | action | 效果 |
|---|---|---|
| 所有 | `close` | 维持现状，结案 |
| 举报 / 私信 | `punish` | 屏蔽消息 + 禁言 `hours` 小时（默认 12，1–720） |
| 举报 / 私信 | `revert` | 恢复消息 + 解除禁言（撤销自动处理） |
| 商品 | `reject` / `restore` | 驳回下架（`note` 作为驳回原因）/ 恢复上架 |
| 申诉 | `accept` / `reject` | 同意（解除禁言或恢复上架）/ 驳回 |
| 资料 | `reset` | 重置昵称、清空简介、锁 24 小时 |

已结案的案件再处理 → 409；这类案件不支持的 action → 400。

## 7. 推送事件

| push | data | 什么时候发 |
|---|---|---|
| `chat.new_message` | `{ Message }` | 有人给你发了私信 |
| `order.updated` | `{ Order }` | 你参与的订单状态变了（被下单、被发货、被确认、被取消） |
| `chat.message_masked` | `{ "message_id", "from_id", "to_id", "masked": true }` | 一条私信被屏蔽（`masked: false` = 管理员撤销了屏蔽），发送方和接收方都会收到 |
| `user.muted` | `{ "muted_until": 1762586400 }` | 你被禁言、禁言加时或解除禁言（`0` = 解除） |
| `goods.reviewed` | `{ "goods_id", "status" }` | 你的商品审核完了：`on_sale` 已上架。AI 判违规驳回时**不推送**，卖家在"我发布的"里看到 |
| `report.result` | `{ "report_id", "status" }` | 你的举报有结果了：`upheld` 成立 / `rejected` 不成立 / `manual` 转人工 |
| `user.profile_reset` | `{ "nickname", "reason", "nickname_locked_until" }` | 你的昵称和简介因违规被重置 |

用户不在线时推送直接丢弃。离线消息不会丢，因为都存在数据库里，上线后用 `chat.conversations` 和 `chat.history` 就能拉到。
