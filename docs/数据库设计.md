# 广理职小鱼 · 数据库设计

数据库用 **SQLite**：整个数据库就是一个文件（`data/xiaoyu.db`），不用另外装数据库软件，SQL 语法和 MySQL 基本一样。
建表语句在 `server/src/core/db.c` 的 `SCHEMA_SQL` 里，服务器启动时自动建表。

## 1. 约定

- **金额**一律用"分"存整数（`INTEGER`），比如 320 元存成 `32000`。不用小数，避免 `0.1 + 0.2 ≠ 0.3` 这种浮点误差。
- **时间**一律用 Unix 时间戳（秒）存整数。
- **状态**用英文单词存（`on_sale`、`paid`），并用 `CHECK` 约束限制只能取这几个值。

## 2. 表之间的关系

```
users ─┬─< sessions          一个用户可以同时在几台电脑登录
       ├─< goods ─┬─< goods_images     一件商品最多 9 张图
       │          └─< favorites >─ users   收藏是用户和商品的多对多
       ├─< orders（买家、卖家都是 users）>─ goods
       └─< messages（发送者、接收者都是 users）
categories ─< goods
```

## 3. 表结构

### users 用户
| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER 主键 | 自增 |
| username | TEXT 唯一 | 登录名，3–20 位字母数字下划线 |
| password_hash | TEXT | `sha256(salt + 密码)` 的十六进制，**不存明文密码** |
| salt | TEXT | 每个用户随机生成的 32 位十六进制"盐" |
| nickname | TEXT | 昵称 |
| avatar | TEXT | 头像图片名，空字符串表示没有 |
| bio | TEXT | 个人简介 |
| balance | INTEGER | 余额（分），`CHECK (balance >= 0)` 保证不会扣成负数 |
| created_at | INTEGER | 注册时间 |

**为什么要加盐**：如果直接存 `sha256(密码)`，密码一样的人哈希也一样，黑客拿到数据库后可以用提前算好的"彩虹表"批量反查。每人一个随机盐，同样的密码哈希也完全不同，彩虹表就失效了。

### sessions 登录令牌
| 字段 | 类型 | 说明 |
|---|---|---|
| token | TEXT 主键 | 64 位随机十六进制 |
| user_id | INTEGER | 属于哪个用户 |
| created_at / expires_at | INTEGER | 创建时间 / 过期时间（7 天） |

登录成功后发一个 token，之后客户端每次请求都带上它，服务器查这张表就知道是谁。退出登录就删掉这一行。

### categories 分类
固定 7 条：数码电子、书籍教材、生活用品、服饰鞋包、运动户外、美妆个护、其他。

### goods 商品
| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER 主键 | |
| seller_id | INTEGER | 卖家 |
| title / description | TEXT | 标题（≤30 字）/ 描述（≤500 字） |
| price / original_price | INTEGER | 售价 / 原价（分），原价 0 表示没填 |
| category_id | INTEGER | 分类 |
| condition | INTEGER | 成色 0 全新 / 1 几乎全新 / 2 轻微使用 / 3 明显使用 |
| status | TEXT | `on_sale` 在售 / `sold` 已卖出 / `off_shelf` 已下架 |
| view_count | INTEGER | 浏览量 |
| created_at / updated_at | INTEGER | |

### goods_images 商品图片
`(goods_id, sort)` 联合主键，`sort = 0` 的是封面。图片文件本身存在 `data/images/` 文件夹，表里只存文件名。

### orders 订单
| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER 主键 | |
| order_no | TEXT 唯一 | 18 位订单号：年月日时分秒 + 4 位随机数 |
| goods_id / buyer_id / seller_id | INTEGER | |
| goods_title / price | TEXT / INTEGER | 下单那一刻的**快照**，卖家之后改商品不影响订单 |
| status | TEXT | `paid` / `shipped` / `completed` / `cancelled` |
| ship_note | TEXT | 发货备注（"明天中午食堂门口"） |
| created_at / shipped_at / completed_at / cancelled_at | INTEGER | 0 表示还没发生 |

### messages 私信
| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER 主键 | 越大越新，分页和排序都靠它 |
| from_id / to_id | INTEGER | 发送者 / 接收者 |
| goods_id | INTEGER | 聊的是哪件商品，0 表示没有 |
| content | TEXT | ≤500 字 |
| is_read | INTEGER | 0 未读 / 1 已读 |
| created_at | INTEGER | |

### favorites 收藏
`(user_id, goods_id)` 联合主键，天然防止重复收藏。

## 4. 索引（为什么查得快）

| 索引 | 给谁用 |
|---|---|
| `goods(status, created_at)` | 首页"在售商品按时间排序" |
| `goods(category_id, status)` | 按分类筛选 |
| `goods(seller_id, status)` | "我发布的"、用户主页 |
| `orders(buyer_id, created_at)`、`orders(seller_id, created_at)` | "我买到的"、"我卖出的" |
| `messages(from_id, to_id, id)` | 两个人的聊天记录 |
| `messages(to_id, is_read)` | 未读数 |
| `orders(goods_id) WHERE status <> 'cancelled'`（**唯一**） | 防超卖的第二道保险，见下节 |

## 5. 防超卖：一件商品不会卖给两个人

两个人同时点"立即购买"，服务器会在两个线程里同时处理。我们用了两道保险：

1. **事务 + 带条件的更新**（`order.create`）
   ```sql
   BEGIN IMMEDIATE;                       -- 一开始就拿写锁，第二个人只能排队等
   UPDATE goods SET status = 'sold' WHERE id = ? AND status = 'on_sale';
   -- 改了 0 行 → 已经被别人买走了 → ROLLBACK，返回 409
   UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?;
   -- 改了 0 行 → 钱不够 → ROLLBACK，返回 402（商品状态也一起回滚）
   INSERT INTO orders ...;
   COMMIT;
   ```
2. **部分唯一索引**：`orders(goods_id) WHERE status <> 'cancelled'`。就算代码有 bug，数据库也不允许同一件商品出现两个有效订单。

实测：10 个用户同时抢同一件商品，恰好 1 个成功，9 个收到"商品已卖出"。
